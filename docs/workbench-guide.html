界面讲解 · 依据当前仓库代码

从打开页面到跑完一次评测

这份手册按你实际看到界面的顺序走：顶部状态条、检索、对比、评测。每个按钮背后只有一个后端接口，每个状态背后只有一条服务端判断。文中标了代码位置，演示前可以逐条核对。

单文件前端，无构建 只读 PGVector OpenAPI 契约 离线评测

先把最重要的一句话放在前面：这个工作台本身不检索任何东西。它是一个单文件 HTML（web/index.html），通过生成的 SDK 调 FastAPI 的四个接口，再把返回的 JSON 画成三栏界面。你在页面上看到的每个数字、每条状态、每个耗时，都是服务端算出来的。

所以演示时不要从「界面功能」讲起，从「一次请求流到哪里」讲起，后面所有按钮都会变得顺理成章。

顶部状态条

品牌区

装饰

左侧的标记、标题和副标题纯展示，不承载任何操作。

健康灯与索引版本

每次打开只查一次

页面启动时请求一次 /healthz。服务端把状态拆成三个维度：connectionAvailable（数据库连得上、账号有效）、schemaReady（表、documents、关键列、HNSW 索引齐全）、corpusCount（符合检索范围的记录数）。健康灯据此显示三态：绿点「PGVector 可用 · N 条」、黄点「已连接 · 表结构未初始化 / 语料为空」、红点「数据库连接失败」。无论哪一态都会显示 indexVersion，形如 pgvector:rag.vector_records_v2_d1024:qwen-embedding-1024。

这串索引版本是「库 + 表 + 向量配置」的指纹。页面只在启动时检查，不会自动重试；数据源修好后要刷新页面。窄屏（小于 760px）会隐藏健康信息，这是样式行为，不是故障。

四个运行按钮的开关规则

关键交互

运行检索、生成答案、运行四种配置、创建评测任务：前三个只在正在跑或 API 不可达时变灰；缺表或语料为空时仍然可以点击，接口会返回空结果并在 statuses.source 里写明 schema_missing。创建评测任务额外要求 schemaReady，因为空表上的评测没有意义。

所以「点不动」只有两种含义：请求还没回来，或者 API 进程不可达。缺表、空语料、数据库连接失败都会给出明确提示，而不是禁用按钮。

只读是代码级的。适配器每次查询都执行 SET TRANSACTION READ ONLY，再发 SQL（rag_service/backend.py:103）。不是靠约定，也不是靠数据库账号权限「应该够用」。
01检索

一次运行：输入、结果、过程

这一页回答两个问题：这段数据能不能被召回？答案能不能被证据支撑？

检索页是默认页，也是唯一同时暴露「候选」和「答案」两条路径的地方。左栏收集输入，中栏放结果，右栏放过程与证据。先把左栏六个控件讲清楚，按钮的行为就不用背了。

左栏：一次运行的输入

查询

输入框

默认值 USB-C 快充 只是演示占位，没有任何业务预填。上限 2000 字符，右下角实时计数。这里输入什么，服务端就把它当原始 query；是否扩展取决于下面的「查询改写」。

页面没有表单提交逻辑，按回车不会触发检索，必须点按钮。演示时先把这一点说清楚，能避免观众下意识敲回车。

配置

下拉 · 四个注册项

四个配置在服务端注册（rag_service/pipeline.py:17），不能自定义组合。高级覆盖项只能改参数，改不了注册表。

配置实际做什么演示时的说法
仅 Dense只走向量相似度召回语义相近、字面不同也能找到
仅 BM25只走全文关键词召回型号、专有名词、精确词更稳
Hybrid 混合两路都跑，再用 RRF 合并默认配置，兼顾语义与关键词
Hybrid + Rerank混合结果再调一次外部精排模型多一个可选环节，不是必然更好

融合用的是 Reciprocal Rank Fusion：每路按名次贡献 1/(k+名次)，k 默认 60。它只看排名，不把 Dense 的余弦分和 BM25 的分数直接相加——两路分值量纲不同，混加没有意义。

TopK

输入框 · 1 到 100

最终展示多少条。注意它不是每路的召回上限：单路召回默认取 max(TopK, 20) 条（pipeline.py:53），融合后再截断到 TopK。

页面的高级覆盖项默认就带着两个 20，并且会被发出去。所以你把 TopK 调到 50、路由 TopK 仍是 20 时，每路还是只有 20 条候选，结果不会凭空变多。演示前把两个路由 TopK 一起调大，才不会翻车。

查询改写

下拉 · 关闭 / 多查询

「多查询」不是大模型改写，是确定性字符串扩展：把「多少」换成「数值」、去掉问号，原句保留，最多三条（pipeline.py:25）。服务端会为每条 query 分别召回，再合并去重。

演示时建议直说「这是确定性的字符串扩展，用来验证多 query 链路」。不要说成 AI 改写——代码里没有任何模型调用。

高级覆盖项

折叠面板

两个输入：Dense 路由 TopK、BM25 路由 TopK，默认 20。只有非零数字才会被发送。

后端白名单还允许 fusion.topK、fusion.rrfK、rerank.candidateTopK、rerank.outputTopK、rerank.enabled，但界面没有暴露。白名单之外的键会被直接拒绝（pipeline.py:44），页面本身发不出任意参数。

两个按钮：检索与答案的分岔

运行检索

POST /v1/retrieve
运行检索主按钮 · 蓝底白字

只做四件事：改写、召回、融合、可选精排，最后排序。它不生成答案，返回的是候选证据和每一步的诊断。

点击后中栏先出现骨架屏，请求返回后替换成结果。骨架屏是占位，不是卡死。

生成答案

POST /v1/answers
生成答案次按钮 · 浅蓝底

请求体和检索相同，另外带答案模型配置和一份固定的 judge:{enabled:false}。服务端会再跑一遍同一套检索，然后把候选做成 Context Pack，过证据门控，调答案模型，最后只接受 Context Pack 里存在的引用编号。

页面从不启用评审（judge）：开关被硬编码为关闭（web/index.html:120）。所以「答案评审」永远是「已跳过」，不是评审服务坏了。

对比项运行检索生成答案
后端接口/v1/retrieve/v1/answers
检索过程跑一次完整检索服务端再跑同一套检索
证据门控没有有：文档、版本、源块、页码缺一项就拒答
输出候选列表 + 阶段诊断答案 + 引用 + Context Pack + 同一份检索诊断
额外调用无答案模型；评审被页面固定关闭
失败时状态失败或降级，仍返回候选状态失败，不编答案，但仍返回 Context Pack 与诊断

中栏：结果怎么读

标题与徽章

状态头

运行检索时显示「检索输出」，生成答案时变成「答案输出」。右侧徽章跟着状态变色：绿为正常或已回答，黄为降级或进行中，红为失败或拒答。

四个指标

先讲这四个
指标检索页显示什么答案页显示什么
状态顶层检索状态顶层答案状态
结果数候选条数Context Pack 条数
置信度—（不适用）高 / 低
总耗时整条检索链路只有检索段，不含生成与校验

置信度是规则分类，不是概率。服务端目前把高分固定为 0.9、低分为 0.0，阈值版本写着 uncalibrated-v1（rag_service/main.py:128）。演示时不要把它说成「90% 正确率」。

答案框

只在答案页出现

只有答案成功（已回答或降级）且有文本时才出现，右上角标是置信度。背景用青绿，是为了和候选列表区分开：这是「结论」，下面的卡片是「依据」。

如果答案是失败或拒答，答案框不出现，但右侧的 Context Pack 和引用区仍然会显示材料。这是故意的：失败也要能复盘。

结果卡片

核心信息密度最高

逐项对应代码里的字段：

编号与类型：检索显示 R1、R2；答案显示 S1、S2（服务端生成的引用编号）。类型是文本、图片或表格，图片和表格按普通内容参与排序，没有单独的检索语义。

排名与 finalScore：有精排分就用精排分，否则用 RRF 分。保留四位小数，方便比较相邻名次。

正文：如果命中的是子块，这里展示父块全文，子块原文放在 matchedText 里（backend.py:66）。目的是给答案模型足够的上下文，而不是一句被切断的话。

溯源标签：文档 ID、版本、页码、源块 ID（最多显示两个）。这些全部来自数据库，不是模型生成的。证据门控就是检查这几项齐不齐。

分路分数：dense、bm25、rrf、rerank 的实际数值，是排查排序问题的主要依据。演示时可以指一下「同一份结果在两种召回里各排多少」。

复制响应

小按钮

把完整 JSON 复制到剪贴板，适合贴给开发排查。复制失败会提示「剪贴板不可用」，页面内容不受影响。

右栏：过程与证据

处理阶段

每步状态与实测耗时

检索固定六行：查询改写、Dense 检索、BM25 检索、融合排序、Rerank 重排、检索。生成答案会在这六行之后追加：证据门控、Context Pack 组装、答案生成、引用校验、答案评审。

圆点颜色只有三档：通过、正常、已发送是绿；跳过、降级、进行中是黄；失败、拒答是红。耗时都是实际测量的，不是估算。某一行显示 0.0 毫秒，通常意味着这一步根本没执行，而不是执行得极快。

Context Pack 与引用

最有说服力的一栏

有引用时显示引用，没有引用时显示 Context Pack。每条包含引用编号、原文、文档、版本、页码、源块。这些就是发给答案模型的全部材料，页面没有隐藏任何「模型自己知道的东西」。

证据门控要求文档 ID、版本、源块列表、页码全部存在且页码大于等于 1，缺一项直接拒答（main.py:74）。引用校验则只接受 Context Pack 里出现过的编号；模型编一个 S9 出来，整个回答会被判为无效。

Langfuse 链路链接只在服务端配置了 Langfuse 并成功发送时出现。没出现不代表链路丢了，只代表没接外部观测。

一句话记住检索页：左栏决定「发什么」，中栏回答「是什么」，右栏证明「凭什么」。演示时按这个顺序讲，观众不会掉队。
02对比

同一个问题，四种配置并排看

对比页不生成答案，只横向比较召回差异。

这一页只有一个输入和一个按钮。它把同一个查询依次发给四个注册配置，每个配置各跑一次检索，然后把结果放进四张卡。用途是在一分钟内说清「换配置到底改变了什么」，比在检索页反复切下拉更直观。

查询

输入框

只影响这一页的四个请求，和检索页的查询互不同步。默认值同样是 USB-C 快充。

运行四种配置

主按钮
运行四种配置

固定 TopK 为 5、改写关闭、不带覆盖项，按 Dense、BM25、Hybrid、Hybrid+Rerank 的顺序依次调用，不是并发。点击后四张卡先一起变成骨架屏，四个请求全部返回后一次性渲染。

因为顺序执行，最慢的一路决定整体等待时间。演示时如果 BM25 索引缺失，那一张卡会直接显示失败，其他三张照常出结果——这正好能讲「单路失败不会拖垮全局」。

四张结果卡

只读 · 会话内

每张卡显示四个信息：结果数（大字）、检索状态、第一条结果的正文预览、最高分。失败时预览位置显示错误文本。

结果只存在当前标签页的内存里，刷新即丢，不落库、不跨设备。每张卡按配置覆盖上一次结果。页面不会自动生成多个答案，也不会把对比结果带进检索页。

适用场景：解释「为什么同一个问题，换配置后第一条变了」。不适用：证明哪种配置「更好」——那需要评测页的固定问题集和指标。
03评测

用固定问题集，量化检索质量

异步创建、轮询取回，不阻塞在线检索。

评测页把「感觉还不错」变成可复现的数字。数据集由服务端注册，页面只负责选择、创建和轮询。当前只注册了一个数据集 fake-eval-v1，包含三条查询和硬编码的相关块编号。

数据集

下拉 · 服务端注册

页面启动时请求 /v1/evaluation-datasets 填充。当前三条查询是「支持多少瓦快充」「USB-C 接口示意图」「额定功率」，分别对应文本、图片、表格三类内容。

数据集不能在前端新增或编辑。要加数据集得改服务端代码，这是刻意的：避免评测标准被临时修改。

配置

下拉

整批评测使用同一个检索配置，不会混合比较。想比较配置，就分别创建两次任务。

启用 Ragas

复选框

勾选后，服务端会逐条调用外部 Ragas 服务，评估上下文与答案质量。没配置 RAGAS_API_URL 时，状态是「已跳过」，不会假装有分。

页面表格只显示 Ragas 的状态（已发送、已跳过、失败），不展示具体指标值；指标在接口返回体里。

创建评测任务

POST · 202
创建评测任务

服务端立即返回一个 runId，任务在后台线程里跑。页面每 100 毫秒查询一次，最多 80 次，也就是约 8 秒。

超过 8 秒还没跑完，页面就不再自动刷新，停留在最后一次状态。需要重新创建任务，或直接查接口。数据源不可用时，创建会返回 503——设计原则是「没有正式数据，就不产出看起来像结果的东西」。

结果表

指标含义

Recall@K：该找到的相关块，找到了多少。
Precision@K：前 K 条里有多少是相关的。
MRR：第一条相关结果排在第几，取倒数；越靠前越高。
nDCG@K：考虑相关性等级（0 到 3）的排序质量，比只看命中更严格。

接口还会返回 P50、P95、P99 延迟、图片与表格命中率、溯源完整率，界面表格没有展示。演示时如果被问「还有没有别的指标」，可以点开接口文档 /docs 补充。

演示前一定先看这一条：评测的标准答案（qrels）是硬编码的块编号 text-001、image-001、table-001。只有当正式数据表里真的存在这些编号时，指标才有意义；对不上时全为 0，这反映的是数据集与数据不匹配，不是检索坏了。主动说明这一点，比被观众问出来更稳。

与 Chunk Lab 的分工

离线负责生产证据，在线负责使用证据。交接点只有一张只读表。

环节谁负责说明
文档解析、切分、人工修订Chunk Lab（离线）本服务不参与，也不修改切分语义
生成向量 embeddingChunk Lab 发布流程写一次；本服务绝不重新计算
建 BM25 索引Chunk Lab 侧迁移脚本本服务只做存在性与唯一性检查
查询 embedding本服务（在线）调配置好的同一套向量模型
召回、融合、精排本服务只读 SQL，不建第二索引
证据门控、答案、引用校验本服务证据与引用都由服务端裁决
评测与观测本服务（离线 / 旁路）Ragas、Langfuse、Judge 都是可选

三条边界，演示时可以直接说

数据只写一次

不会双写

向量由 Chunk Lab 的发布流程写入正式表。本服务不创建第二套索引、不重新 embedding、不写向量表。所以「检索结果和 Chunk Lab 看到的不一致」这类问题，根因通常在发布环节，不在这里。

连接是只读的

代码级

每次查询新开连接，先声明只读事务，再执行 SQL。数据库报错会被统一包装成「后端不可用」，既不泄露凭据，也不会悄悄降级成别的实现。

入口不带参数

全局检索

Chunk Lab 只提供一个无参数的新标签页按钮，指向配置好的工作台地址。它不携带任务、记录、向量、过滤条件、密钥或回跳地址。所以这里永远没有「商品范围」「校验任务」这类上下文，也不会从浏览器接收检索记录。

一句话总结边界：Chunk Lab 决定「知识长什么样」，AgenticRetrival 决定「怎么把知识找出来并给出可核对的答案」。两边只通过一张只读表交接。

为什么「已跳过」不算失败：这个服务的设计原则是「明确状态优于静默降级」。可选组件没配置就明说没配置，而不是拿一个相似的东西顶上，让人误以为它工作了。

线下演示动线

建议 8 到 10 分钟。每一步都写了一个可以直接照着说的话头。

演示前 5 分钟检查

  • 打开页面，确认右上角 PGVector 是绿点，并记下索引版本。
  • 用 Hybrid 跑一次「USB-C 快充」，确认有结果、阶段没有大面积红色。
  • 确认服务端是否配置了答案模型。没配时，点「生成答案」会得到失败和「答案模型不可用」，这本身是可讲的显式状态，但你要提前知道。
  • 确认是否配置了精排。没配时，Hybrid + Rerank 会显示「Rerank 已跳过、检索已降级」。
  • 挑一条页码和源块都齐全的结果，作为「溯源完整」的正面例子。
  • 把浏览器缩放到 100%，确认右栏的引用不需要横向滚动。

开场：先讲边界，再讲界面

指向右上角健康灯和索引版本。说明这个页面不查库，后面的 Python 服务查；服务连的是 Chunk Lab 离线发布出来的只读向量表。

「离线负责把知识变成可检索的证据，在线负责只读地找证据。界面上所有数字都来自服务端，浏览器不做任何检索计算。」

跑一次检索

配置选 Hybrid，TopK 5，点「运行检索」。按中栏四个指标、右栏阶段耗时、第一条结果的顺序讲。

「排序用的是 RRF，只合并名次，不把两路的原始分相加。右栏每一行都是实测耗时，不是估算。」

换配置，看差异

切到仅 Dense 再跑一次，指出阶段栏里的 BM25 变成「已跳过」，结果可能变化。条件允许的话再切仅 BM25。

「四个配置是服务端注册的，前端改不了组合。这里换的是召回策略，不是换个说法。」

讲可选精排

切到 Hybrid + Rerank。已配置时看 rerank 变成「已发送」并重新排序；未配置时是「已跳过」，整体检索标记为「已降级」。

「可选服务不可用不会被伪装成成功。降级是明确写在状态里的。」

生成答案

点「生成答案」。先看答案框，再看右栏 S1、S2 引用和 Context Pack，最后指一下「答案评审」是跳过。

「模型只能引用服务端给它的编号。编一个不存在的编号，整个回答会被判为无效。评审默认关闭，不参与在线判断。」

对比页

切到对比，输入同一个问题，点「运行四种配置」。等四张卡出来后，比较结果数和第一条预览。

「四种配置各跑一次，结果只在当前会话里，刷新就没了。它的用途是解释差异，不是评优劣。」

评测页

选数据集和配置，点「创建评测任务」，看表格出现。主动说明 qrels 与正式数据的匹配问题。

「评测是异步的，页面最多等八秒。指标里的 Recall 和 nDCG 衡量召回与排序质量；标准答案是硬编码的，对不上正式数据时指标会很低，这反映数据集而不是检索故障。」

收尾

回到架构图，用一句话收束。

「Chunk Lab 决定知识长什么样，这里决定怎么找到它，并且让每一个结论都能点回原文。」
三句不要说错的话：多查询改写不是大模型做的；置信度 0.9 不是 90% 正确率；Rerank 显示跳过不是故障。

常见问题

按观众最可能追问的顺序排列。

Rerank 为什么显示「已跳过」？

两种原因。第一，当前配置是 Hybrid，它本身不含精排环节，只有 Hybrid + Rerank 才会调用。第二，配置切过去了，但服务端没设精排地址和密钥，调用被安全地跳过，同时检索状态降为「已降级」。两种情况下都不会伪造精排分数。

为什么所有运行按钮都是灰的？

页面打开时只查一次健康检查。数据源不可用，或者有请求正在跑，四个按钮就一起禁用。修好数据库后需要刷新页面，它不会自动重试。

点「生成答案」直接失败，是不是坏了？

如果原因是「答案模型不可用」，说明服务端没有配置答案模型（地址和密钥）。这是显式失败，不是异常崩溃；检索诊断和 Context Pack 仍然会返回。配置 RAG_ANSWER_PROVIDER、RAG_ANSWER_BASE_URL、RAG_ANSWER_API_KEY 后重启服务即可。

置信度为什么只有高和低，分数为什么固定？

当前阈值是启发式的，版本号明确写着 uncalibrated-v1。服务端在通过引用校验时给 0.9，否则给 0.0，等级按规则划分。它表达的是「证据链是否完整」，不是概率。要真正标定，需要人工标注集。

答案页的「总耗时」为什么比阶段加起来还少？

因为答案页的这个数字取的是检索段耗时，不含答案生成和引用校验。想看完整耗时，把右栏的阶段耗时逐个加起来，或者看接口返回里的各阶段值。

把 TopK 调大，结果为什么没变多？

高级覆盖项里两个路由 TopK 默认是 20，并且会随请求发送。它们限制了每路候选数量。要真正扩大召回，把这两个值一起调大，再调大 TopK。

评测指标全是 0，怎么排查？

先看评测数据集的相关块编号在正式表里是否存在（当前是 text-001 这类固定编号）。对不上时指标必然为 0。其次确认创建任务时数据源可用，且用的是预期的配置。最后才怀疑检索逻辑。

这个页面会修改数据库吗？

不会。服务端每次查询都先声明只读事务，页面也没有任何写入接口。连「重新 embedding」或「重建索引」的路径都不存在。
